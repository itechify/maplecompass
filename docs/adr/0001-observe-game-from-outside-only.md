# Observe the game from outside only

MapleCompass must not be seen as interacting with the MapleStory client, because third-party interaction can breach the terms of service and get the player's account banned. So it only reads pixels through the operating system's ordinary screen-capture APIs, and it only draws in its own separate windows. It never reads or writes the game's memory or files at runtime, never injects code or hooks the renderer, and never sends input to the game.

The overlay panel is always clickable: wherever it shows, a click on it lands on MapleCompass and the game doesn't see it, just as with any other window in front of the game. The player drags the panel by its header and clicks its buttons at any time. A click never takes the keyboard from the game, though: the overlay is a no-activate window (`WS_EX_NOACTIVATE`), so Windows leaves the game as the active window. While there is no game window to show the panel over, the overlay draws nothing and lets every click through. The Grind Tracker's window is the same kind of window: always clickable, no-activate, kept just above the game, and hidden while there is no game window. So is the Item Lookup alert's (ADR 0007), at the top centre of the game window for a few seconds after an Item Lookup, except that it lets every click through to the game unless it lists items to pick from. The region-marking window is the other window of ours that takes the mouse over the game, while the player drags a box around the minimap title (or the EXP bar) at setup.

The search view is the only time the overlay takes the keyboard. The search hotkey or a click on one of the panel's 🔍 buttons opens it: the overlay becomes focusable and comes to the front with `SetForegroundWindow` on our own window, right after that hotkey or click, like any app window the player switches to, so their typing and keys go to it. Pressing the hotkey again with the view open brings the overlay back in front the same way. Picking a map, the back arrow, Esc, or switching to the game or another app closes the view. The overlay is then no-activate again; if it still has the foreground, it hides and shows itself again without activating, so Windows gives focus back to the window below it, the game. Nothing is sent to the game at any point.

Keyboard input comes only through global hotkeys registered with the operating system (`RegisterHotKey` on Windows): the system tells us when the player presses one of our combinations. There are no low-level keyboard hooks (`WH_KEYBOARD_LL`) and no polling of key state (`GetAsyncKeyState`). A registered combination reaches no other window, so the hotkeys are registered only while the game or one of our windows is in front, and released as soon as another app is. We tell which window is in front with `GetForegroundWindow`, polled as the z-order keeper already does, so other apps keep their own shortcuts. The defaults are Ctrl+Shift+letter. Win+Alt+letter was tried first, to stay clear of what players bind in the game, but Windows and other apps already hold many of those letters (Win+Alt+F was taken on the owner's machine). So we accept that a Ctrl+Shift combination we register is lost to the game while it is in front, and a player who binds one in the game rebinds ours in the settings file.

## Consequences

The map has to be inferred from the rendered minimap title (OCR or glyph matching) rather than read directly. Shortcuts such as reading the current map ID from process memory are permanently off the table, even though they would be more accurate.

To stay at the game's level in the z-order, rather than on top of every app, the overlay (and likewise the Grind Tracker's window) is kept just above the game by polling the window order and restacking only our own window (`SetWindowPos` with no activation). Making the overlay an owned or child window of the game (`GWLP_HWNDPARENT`, `SetParent`) would do this for free, but it is ruled out: a cross-process owner or parent link attaches our input queue to the game's, which is interaction with the game client. Window-event hooks (`SetWinEventHook`) are avoided for the same reason.

Our windows are not hidden from screen capture, so the panel shows in the player's screenshots and streams. Our own capture of the Title Region (and of the EXP Bar Region) would then read the panel if it covered them, so the core never places the panel there: inside the game window it moves clear of every captured region, whether at its default spot or where the player dragged it. The Grind Tracker's window and the Item Lookup alert move clear of them the same way.
